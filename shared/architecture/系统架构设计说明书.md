# 在线生鲜商城系统架构设计说明书

**版本**：V1.0  
**日期**：2026-06-30  
**适用范围**：两周暑期实训项目  
**技术约束**：Flask + SQLite + Bootstrap，单体架构，Flask/Jinja2 服务端渲染，不做前后端分离，不做登录、支付、订单。

---

## 1. 技术选型说明

### 1.1 Flask

系统采用 Flask 作为后端 Web 框架。Flask 轻量、依赖少、学习成本低，适合两周实训周期内快速完成可演示系统。项目功能集中在商品浏览、分类筛选、购物车管理和低库存预警，不涉及复杂认证、支付或分布式能力，因此无需使用重量级框架。

Flask 与 Jinja2 模板结合紧密，适合采用服务端渲染模式。所有页面由后端路由查询数据后直接渲染 HTML，浏览器只负责展示页面和提交表单，不需要单独建设前端工程。

### 1.2 SQLite

系统采用 SQLite 保存商品、库存和购物车记录。SQLite 不需要独立数据库服务，环境搭建简单，数据库文件可随项目一起管理，适合实训项目本地运行和成果演示。

本项目数据规模较小，主要表为商品表和购物车表，SQLite 的查询与事务能力能够满足需求。首次启动时可自动创建表结构并插入示例商品，保证系统可快速运行。

### 1.3 Bootstrap

页面样式采用 Bootstrap。商品卡片、分类导航、购物车区域、预警横幅、按钮和提示信息均可基于 Bootstrap 组件实现，减少自定义 CSS 工作量，使开发重点集中在业务闭环上。

### 1.4 服务端渲染

系统不做前后端分离，不引入 Vue、React 等前端框架。浏览器通过 GET 请求访问页面，通过 POST 表单提交购物车操作，Flask 处理后重定向并重新渲染页面。

## 2. 系统分层架构

系统采用单体架构，按职责划分为展示层、路由控制层、业务服务层、数据访问层和数据存储层。

```text
浏览器
  -> Flask 路由控制层
  -> 业务服务层
  -> 数据访问层
  -> SQLite 数据库
```

### 2.1 展示层

展示层由 Jinja2 模板和 Bootstrap 样式组成，负责展示商品列表、分类导航、购物车、低库存预警横幅和操作提示。模板只负责展示和简单判断，不直接编写复杂业务逻辑。

### 2.2 路由控制层

路由控制层由 Flask 路由函数组成，负责接收请求、读取参数、调用业务服务并返回页面。建议路由包括：

| 路由 | 方法 | 说明 |
|------|------|------|
| `/` | GET | 首页，展示全部商品、购物车和预警信息 |
| `/category/<category>` | GET | 按分类展示商品 |
| `/cart/add/<product_id>` | POST | 加入购物车 |
| `/cart/update/<product_id>` | POST | 修改购物车数量 |
| `/cart/remove/<product_id>` | POST | 移除购物车商品 |

### 2.3 业务服务层

业务服务层负责商品查询、分类过滤、购物车增删改、数量校验、总价计算和低库存预警生成。业务规则应集中在服务函数中，避免散落在路由和模板里。

### 2.4 数据访问层

数据访问层负责 SQLite 连接、SQL 查询、SQL 更新、表结构初始化和示例数据初始化。建议将商品相关 SQL 和购物车相关 SQL 分别封装，便于调试和维护。

### 2.5 数据存储层

数据存储层为 SQLite 数据库文件，至少包含 `products` 和 `cart` 两张表。商品、库存和购物车记录均持久化保存，页面刷新后数据不丢失。

## 3. 功能模块划分

### 3.1 商品浏览模块

负责从数据库读取商品数据，并以卡片形式展示商品名称、图片、单价、库存和分类。库存为 0 时，“加入购物车”按钮应置灰或不可提交。

### 3.2 分类筛选模块

负责展示“全部、蔬菜、水果、肉类、鱼类”分类入口，并根据分类参数查询商品。分类参数必须做白名单校验，非法分类应重定向到首页或显示空结果提示。

### 3.3 购物车管理模块

负责加入购物车、修改数量、删除商品、展示购物车明细和计算总价。购物车只作为选购清单，任何购物车操作都只修改 `cart` 表，不扣减 `products.stock`。

购物车规则如下：

1. 同一商品重复加入时，购物车数量累加。
2. 购物车数量不能超过商品当前库存。
3. 修改数量为 0 时删除该购物车记录。
4. 商品库存为 0 时不能加入购物车。

### 3.4 库存展示模块

负责在商品卡片和购物车区域展示当前库存。由于本系统不做支付和订单，库存字段只表示数据库中的商品当前库存，不会因加入购物车而减少。

### 3.5 低库存预警模块

负责判断库存是否低于阈值，并生成页面顶部预警横幅。预警对所有访问者可见，因为系统不做登录和权限区分。

### 3.6 数据初始化模块

负责首次运行时创建数据库表，并在商品表为空时插入示例商品。示例数据应覆盖蔬菜、水果、肉类、鱼类四类，并至少包含 1 到 2 个低库存商品，便于演示预警效果。

## 4. 页面结构设计

### 4.1 页面总体布局

```text
顶部区域：系统标题、分类导航、低库存预警横幅
主体区域：商品卡片网格
侧边或底部区域：购物车清单、数量调整、删除按钮、总价
底部区域：项目说明或简单版权信息
```

### 4.2 首页

首页路由为 `GET /`，展示全部商品、购物车明细和低库存预警。页面渲染数据建议包括：

| 数据项 | 说明 |
|--------|------|
| `products` | 商品列表 |
| `categories` | 分类列表 |
| `current_category` | 当前分类，首页为“全部” |
| `cart_items` | 购物车明细 |
| `cart_total` | 购物车总价 |
| `low_stock_items` | 低库存商品列表 |
| `message` | 操作提示信息 |

### 4.3 分类页

分类页路由为 `GET /category/<category>`，复用首页模板，仅改变商品查询条件和当前分类高亮状态。页面仍然展示购物车和低库存预警。

### 4.4 购物车操作

购物车操作不单独设计页面。用户提交 POST 请求后，后端完成处理并重定向回首页或来源分类页。操作结果通过 Flask `flash` 消息或查询参数展示。

## 5. 数据流说明

### 5.1 页面加载数据流

```text
用户访问首页或分类页
  -> Flask 接收 GET 请求
  -> 查询商品列表
  -> 查询购物车明细
  -> 查询低库存商品
  -> 组装模板数据
  -> Jinja2 渲染 HTML
  -> 浏览器展示页面
```

页面每次加载都会重新查询数据库，确保商品、购物车和低库存预警信息与 SQLite 保持一致。

### 5.2 加入购物车数据流

```text
用户点击“加入购物车”
  -> 提交 POST 请求
  -> 查询商品是否存在
  -> 判断库存是否大于 0
  -> 查询购物车中是否已有该商品
  -> 校验加购后数量是否超过库存
  -> 插入或更新 cart 表
  -> 重新触发低库存检测
  -> 重定向并刷新页面
```

关键规则：加入购物车不修改 `products.stock`。

### 5.3 修改购物车数量数据流

```text
用户修改购物车数量
  -> 提交 POST 请求
  -> 查询商品当前库存
  -> 校验目标数量不能超过库存
  -> 数量为 0 时删除记录
  -> 数量大于 0 时更新 cart 表
  -> 重新触发低库存检测
  -> 重定向并刷新页面
```

### 5.4 删除购物车商品数据流

```text
用户点击删除
  -> 提交 POST 请求
  -> 删除 cart 表中对应商品记录
  -> 查询最新购物车
  -> 重新触发低库存检测
  -> 重定向并刷新页面
```

## 6. 数据库设计概要

### 6.1 商品表：products

| 字段名 | 类型 | 约束 | 说明 |
|--------|------|------|------|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | 商品 ID |
| `name` | TEXT | NOT NULL | 商品名称 |
| `category` | TEXT | NOT NULL | 分类：蔬菜、水果、肉类、鱼类 |
| `price` | REAL | NOT NULL | 单价 |
| `stock` | INTEGER | NOT NULL DEFAULT 0 | 当前库存 |
| `threshold` | INTEGER | NOT NULL DEFAULT 10 | 低库存阈值 |
| `image_url` | TEXT | 可为空 | 商品图片路径或 URL |
| `created_at` | TEXT | 可为空 | 创建时间 |

建议为 `category` 建立索引，提升分类查询清晰度和性能：

```sql
CREATE INDEX idx_products_category ON products(category);
```

### 6.2 购物车表：cart

| 字段名 | 类型 | 约束 | 说明 |
|--------|------|------|------|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | 购物车记录 ID |
| `product_id` | INTEGER | NOT NULL | 商品 ID |
| `quantity` | INTEGER | NOT NULL DEFAULT 1 | 加购数量 |
| `updated_at` | TEXT | 可为空 | 更新时间 |

建议约束：

```sql
UNIQUE(product_id)
FOREIGN KEY(product_id) REFERENCES products(id)
```

由于不做登录，系统默认只有一个全局购物车，不设计 `user_id` 字段。

## 7. 低库存预警机制设计

### 7.1 判断规则

低库存判断基于商品表字段：

```text
stock < threshold
```

当商品当前库存小于预设阈值时，商品进入预警列表；否则不显示预警。

### 7.2 触发时机

低库存预警在以下场景触发：

1. 首页加载时。
2. 分类页加载时。
3. 加入购物车后。
4. 修改购物车数量后。
5. 删除购物车商品后。

### 7.3 推荐实现

在业务服务层提供统一方法：

```python
def get_low_stock_items():
    """返回库存低于阈值的商品列表。"""
    pass
```

页面渲染前统一调用该方法，并将结果传入模板：

```python
return render_template(
    "index.html",
    products=products,
    cart_items=cart_items,
    low_stock_items=low_stock_items
)
```

模板中根据 `low_stock_items` 是否为空决定是否展示 Bootstrap 警告横幅。

### 7.4 与购物车关系

购物车变动后会重新触发低库存检测，但购物车变动不会扣减库存。因此预警结果只由 `products.stock` 和 `products.threshold` 决定，不直接受 `cart.quantity` 影响。

## 8. 技术风险和应对方案

| 风险 | 影响 | 应对方案 |
|------|------|----------|
| 需求范围扩大 | 两周内无法完成 | 严格不做登录、支付、订单和前后端分离 |
| 购物车误扣库存 | 业务规则错误 | 规定购物车操作只修改 `cart` 表，不修改 `products.stock` |
| 路由逻辑过重 | 后期难维护 | 将商品、购物车、预警逻辑封装为服务函数 |
| SQLite 初始化失败 | 首次运行无法演示 | 启动时检查表结构，商品为空时自动插入示例数据 |
| 分类参数非法 | 页面报错 | 对分类做白名单校验 |
| 数量校验遗漏 | 购物车数量超过库存 | 加购和修改数量两个入口都校验库存上限 |
| 页面提示不清晰 | 用户不知道操作结果 | 使用 Bootstrap alert 或 Flask flash 展示提示 |
| UI 开发耗时 | 影响核心功能 | 优先使用 Bootstrap 现成组件 |

## 11. 验收关注点

1. 首页能展示所有商品，数据来自 SQLite。
2. 四个分类筛选均能正确工作。
3. 商品库存为 0 时不能加入购物车。
4. 购物车数量不能超过商品库存。
5. 加入购物车、修改购物车、删除购物车不会扣减库存。
6. 刷新页面后购物车记录仍然存在。
7. 页面加载时能显示低库存预警。
8. 购物车变动后页面重新加载并重新检测低库存预警。
9. 所有页面均由 Flask/Jinja2 服务端渲染。
10. 不存在登录、支付、订单和前后端分离实现。

## 12. 结论

本系统采用 Flask + SQLite + Bootstrap 的单体服务端渲染架构，技术栈轻量，结构清晰，适合两周实训完成。设计重点是控制系统边界，将开发范围集中在商品浏览、分类筛选、购物车选购清单、数据持久化和低库存预警。

后续开发时应优先完成数据库初始化和商品展示，再实现购物车管理，最后补齐低库存预警和页面体验优化。购物车不扣减库存、低库存预警在页面加载和购物车变动后触发，是实现过程中必须严格遵守的核心规则。
